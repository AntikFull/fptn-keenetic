# План исправления нагрузки и зависаний FPTN на Keenetic

Версия репозитория на момент анализа: `v1.1.22-keenetic` (HEAD `0757d35`).

## Краткий диагноз

Зависание — не одна ошибка, а сумма пяти независимых причин. Две из них — в C++ (постоянный busy-spin), одна — утечка ОЗУ через логи в tmpfs, одна — конфликт настроек интерфейса, приводящий к «шторму» демона `ndm`, и одна — накопление правил iptables. Веб-панель и watchdog добавляют постоянный фон.

Ключевой момент: **проблема есть даже когда туннель простаивает и трафика нет.** Это указывает именно на busy-spin, а не на нехватку производительности при шифровании.

---

## Критические причины

### C1. Busy-spin в WebSocket-клиенте (главный потребитель CPU)

`src/fptn-protocol-lib/https/websocket_client/websocket_client.cpp:118-124`

```cpp
while (running_ || !was_stopped_) {
  const std::size_t processed = ioc_.poll_one();
  if (processed == 0) {
    std::this_thread::sleep_for(std::chrono::milliseconds(1));
  }
}
```

`poll_one()` не блокируется. В простое это ~1000 итераций/сек и ~2000 системных вызовов/сек (`poll` + `nanosleep`), непрерывно, всё время работы клиента. На x86 это незаметно, на Cortex-A53 роутера — постоянная заметная загрузка ядра.

**Исправление:** заменить на блокирующий `ioc_.run()` с `boost::asio::executor_work_guard`, останов — через `ioc_.stop()` / сброс work guard. Никакого sleep-цикла.

### C2. Busy-spin в читателе TUN-интерфейса

`src/common/network/net_interface.h:264-285` — неблокирующее чтение и `sleep_for(1ms)` при пустом результате.
Причина: `src/common/network/tun/linux_tun_device.h:44` — `tun_->nonblocking(true)`.

Тот же счёт: ~2000 syscall/сек в простое. Плюс второй эффект — гранулярность 1 мс ограничивает пропускную способность и добавляет задержку под нагрузкой (это и ощущается как «зависает»).

**Исправление:** перевести fd в блокирующий режим и ждать через `poll()`/`select()` с таймаутом ~200 мс; для корректного завершения добавить `eventfd`/self-pipe в набор дескрипторов.

### C3. Логи пишутся в ОЗУ — до 36 МБ

`src/common/logger/logger.h:63,88`

```cpp
const std::filesystem::path log_dir = "/var/log/fptn/";
...
rotating_file_sink_mt(log_file.string(), 12 * 1024 * 1024, 3, true);
logger->flush_on(spdlog::level::debug);
```

На KeeneticOS корень — read-only squashfs, а `/var` — **tmpfs, то есть ОЗУ**. Ротация 12 МБ × 3 = до 36 МБ логов, размещённых в оперативной памяти. На роутере с 256 МБ, где уже работают Entware, lighttpd и php-cgi, это прямой путь к нехватке памяти и OOM — то есть к зависанию. `flush_on(debug)` заставляет сбрасывать буфер на каждой строке.

Проверить на роутере: `df -h /var/log && du -sh /var/log/fptn`

**Исправление:** для сборки под роутер использовать `/opt/var/log/` (USB-накопитель), уменьшить до 1 МБ × 2, `flush_on(spdlog::level::err)`, уровень по умолчанию `warn`, убрать `%s:%#` из паттерна.

### C4. Конфликт адресации туннеля → «шторм» демона `ndm`

Три разных адреса и маски прописываются в разных местах одной и той же установки:

| Файл | Что задаётся |
|---|---|
| `install.sh:315` | `ip address 10.0.0.1 255.255.255.255` |
| `install.sh:419-421` | `ip address 172.20.0.2 255.255.0.0` + `ip defaultgateway 172.20.0.1` |
| `S53fptn-client` POSTCMD | `ndmc ... ip address 10.0.0.1 255.255.255.255`, затем `ip addr add 10.0.0.1/8` |

То есть на одном интерфейсе последовательно назначаются `/32`, `/16` и `/8`, причём `ndmc` и прямой `ip addr` задают **разные маски одного адреса**. Демон `ndm` держит собственную модель конфигурации и непрерывно пытается привести ядро в соответствие своему конфигу — при расхождении это уходит в цикл переконфигурации, `ndm` съедает CPU, маршруты флапают, веб-морда роутера перестаёт отвечать.

Дополнительно `ip defaultgateway 172.20.0.1` указывает на шлюз, которого не существует — постоянные попытки установить нерабочий маршрут по умолчанию.

История коммитов подтверждает, что это место не устоялось: `61cb569`, `c885ecf`, `0757d35` — адрес менялся между `10.0.0.1/8`, `172.31.254.1` и `172.20.0.2` за один день.

**Исправление:** один источник истины. Оставить только `ndmc` (или только `ip`), один адрес с одной маской, `ip defaultgateway` удалить полностью. Из `S53fptn-client` убрать дублирующее назначение адреса — интерфейс уже настроен установщиком.

### C5. Правила iptables накапливаются при каждом перезапуске

`S53fptn-client`, POSTCMD — четыре правила через `-I ... 1` (вставка в начало), при этом в PRECMD/stop нет ни одного `-D`:

```
iptables -t nat -I POSTROUTING 1 -o ${IFNAME} -j MASQUERADE
iptables -I FORWARD 1 -o ${IFNAME} -j ACCEPT
iptables -I FORWARD 1 -i ${IFNAME} -j ACCEPT
iptables -t mangle -I POSTROUTING 1 -o ${IFNAME} -p tcp ... TCPMSS
```

Watchdog перезапускает службу до 3 раз за 20 минут, плюс перезапуски из веб-панели. Каждый цикл добавляет 4 дубликата, которые никогда не удаляются → цепочки растут неограниченно → накладные расходы на каждый пакет растут вместе с ними.

Отдельно: журнал в `CLAUDE.md` для v1.0.6 прямо фиксирует «Удалены жесткие вызовы `MASQUERADE` и `TCPMSS`, передав управление NAT демону `ndm`». В текущем коде они вернулись — регрессия.

**Исправление:** либо удалить их совсем (NAT отдать `ndm`, MSS — через `ndmc ... ip tcp adjust-mss pmtu`), либо перед каждым `-I` делать `while iptables -D <то же правило> 2>/dev/null; do :; done`.

## Существенные причины

### H1. `FindServerByLogin` создаёт detached-потоки с TLS-рукопожатиями

`src/fptn-client/utils/speed_estimator/speed_estimator.cpp:86,140`

Запускается N/2 потоков (`.detach()`), каждый — полное TLS-рукопожатие плюс POST. Функция возвращает управление по первому успеху, но **остальные потоки продолжают работать** — их нельзя ни дождаться, ни отменить. При 20 серверах в токене это 10 одновременных ECDHE-рукопожатий с проверкой сертификатов на каждом старте клиента. В сочетании с перезапусками watchdog даёт всплеск, из которого роутер выходит не сразу.

**Исправление:** ограничить параллелизм до 2, добавить общий флаг остановки, чтобы проигравшие завершались сразу, использовать `join` вместо `detach`.

### H2. В веб-панели два одновременных таймера опроса

`deploy/keenetic/index.php:1217` — `setInterval(fetchRealtimeStatus, 3000)`
`deploy/keenetic/index.php:1621` — второй `setInterval(..., 5000)` на тот же `?ajax=get_status`

Оба обработчика делают одно и то же и обновляют те же DOM-элементы — второй добавили, первый не убрали. Итого 32 запроса в минуту; каждый порождает процесс `php-cgi` плюс два `pgrep` и `ip addr`. Открытая вкладка с панелью = постоянная фоновая нагрузка на роутер.

**Исправление:** удалить один таймер, интервал поднять до 10 секунд, останавливать опрос при `document.hidden`.

### H3. Watchdog раз в минуту, с четырёхсекундным пингом

`install.sh:456` — `*/1 * * * * root /opt/bin/fptn-watchdog.sh`, внутри `ping -c 2 -W 2 1.1.1.1` (до 4 секунд) и два `grep` по лог-файлу.

**Исправление:** `*/5 * * * *`, один `ping -c 1 -W 2`.

### H4. Failback в watchdog не работает — неверный путь к логу

`fptn-watchdog.sh:96-97` читает `/opt/var/log/fptn-client.log`, а клиент по `logger.h` пишет в `/var/log/fptn/fptn-client-cli.log` (это же расхождение видно и в `KEENETIC_RECOVERY.md`, где указан второй путь). Файл не существует → `grep` всегда пуст → автовозврат на приоритетный сервер не срабатывает никогда.

**Исправление:** привести путь к одному значению вместе с C3.

## Средний приоритет

**M1. Бинарник 49 МБ не очищен от отладочной информации.**
`file deploy/keenetic/bin/fptn-client-cli-aarch64` → `not stripped, with debug_info`. Занимает место на накопителе, замедляет загрузку. `aarch64-linux-gnu-strip` даст примерно 8–12 МБ. Для сборки под роутер добавить `-Os -ffunction-sections -fdata-sections -Wl,--gc-sections -Wl,-s`.

**M2. `fptn-passwd-aarch64` собран под x86-64.**
`file` показывает `ELF 64-bit LSB pie executable, x86-64` при имени с суффиксом `-aarch64`. На роутере не запустится.

**M3. Переподключение: 35 попыток с интервалом 300 мс.**
`client.h:55` (`kMaxReconnectionAttempts_ = 35`) и `client.cpp:177` (`kReconnectionDelay = 300ms`). При недоступном сервере это 35 TLS-рукопожатий за ~10 секунд — всплеск CPU, накладывающийся на перезапуски watchdog. Нужен экспоненциальный backoff: 0.5 с → 30 с, попыток меньше.

**M4. Гигиена репозитория.**
В корне лежат ~60 сгенерированных Conan файлов `*-release-x86_64-*.cmake`, каталог `build/`, x86-бинарник `fptn-client-cli` на 49 МБ, 18 файлов `release_v1.1.*_report.txt`, `test_*.php`, `update_conf.py`. При этом `git status` показывает изменёнными вообще все файлы проекта — похоже на порчу переводов строк из-за отсутствия `.gitattributes`. Это делает ревью и поиск регрессий практически невозможным, а установка идёт как раз через raw-загрузку из этого репозитория.

**M5. `CLAUDE.md` отстал от кода.**
Журнал описан до `v1.0.6`, фактическая версия — `v1.1.22`. Шестнадцать релизов за один день не задокументированы, поэтому регрессия C5 (возврат MASQUERADE/TCPMSS) осталась незамеченной.

## Порядок работ

Сначала то, что даёт эффект без перекомпиляции — так можно проверить гипотезу на живом роутере за 10 минут.

### Этап 0 — снять замеры (обязательно до правок)

```bash
top -b -n 1 | head -20                  # кто именно грузит: ndm или fptn-client-cli
cat /proc/loadavg
free
df -h /var/log && du -sh /var/log/fptn  # проверка C3
iptables -t nat -L POSTROUTING -n --line-numbers | wc -l   # проверка C5
ip addr show opkgtun1
```
**Критерий:** зафиксировано, какой процесс потребляет CPU. Если это `ndm` — первопричина C4. Если `fptn-client-cli` — C1/C2. Скорее всего оба.

### Этап 1 — правки только в скриптах (без сборки)

1. `S53fptn-client`: убрать назначение адреса, оставив его установщику → проверка: `ip addr show opkgtun1` показывает один адрес с одной маской, `top` не показывает `ndm` в топе.
2. `S53fptn-client`: убрать 4 вызова `iptables -I` (или добавить `-D` перед ними) → проверка: после 5 перезапусков службы `iptables -t nat -L POSTROUTING -n | wc -l` не растёт.
3. `install.sh`: удалить блок 419-423 либо блок 315-317 (оставить один), обязательно убрать `ip defaultgateway 172.20.0.1` → проверка: `ndmc -c "show interface OpkgTun1"` без ошибок, `ip route` без маршрута на несуществующий шлюз.
4. `index.php`: удалить дублирующий `setInterval` (строка 1621), у оставшегося интервал 10000, добавить проверку `document.hidden` → проверка: в DevTools ровно один запрос `get_status` за 10 секунд.
5. `install.sh:456`: cron `*/5`; `fptn-watchdog.sh`: `ping -c 1 -W 2` → проверка: `cat /opt/etc/crontab`.
6. `fptn-watchdog.sh`: путь к логу привести к фактическому → проверка: `grep` в watchdog находит файл.

### Этап 2 — правки в C++ (требуют сборки)

7. C3 (логи): путь `/opt/var/log/`, 1 МБ × 2, `flush_on(err)`, уровень `warn` → проверка: `du -sh /opt/var/log`, `free` стабильна за час работы.
8. C1: `ioc_.run()` + work guard вместо spin → проверка: `top -H -p $(pgrep fptn-client-cli)`, поток websocket в простое ~0% CPU.
9. C2: блокирующее чтение TUN через `poll()` → проверка: `strace -c -p <pid>` за 10 секунд простоя даёт единицы вызовов вместо десятков тысяч.
10. H1: параллелизм 2, флаг остановки, `join` → проверка: `top -H` при старте не показывает 10 потоков.
11. M3: экспоненциальный backoff → проверка: в логе интервалы растут 0.5/1/2/4 с.

**Общий критерий приёмки этапа 2:** при поднятом туннеле и нулевом трафике суммарная загрузка CPU процессом `fptn-client-cli` — менее 2%; `free` не убывает монотонно за час; веб-интерфейс роутера отвечает без задержек.

### Этап 3 — сборка и гигиена

12. Собрать релиз с `-Os` и `-Wl,-s`, проверить `file` (aarch64, stripped) и размер (< 15 МБ).
13. Пересобрать `fptn-passwd` под aarch64 (M2).
14. Добавить `.gitattributes` (`* text=auto eol=lf`), внести в `.gitignore` сгенерированные Conan-файлы, `build/`, `release_*_report.txt`, бинарники; удалить их из индекса.
15. Обновить `CLAUDE.md` (журнал v1.0.7 … v1.1.22 + текущие правки) и версию во всех четырёх обязательных файлах согласно правилу релиза.

## Что требует решения перед реализацией

1. **Какой адрес считать правильным для туннеля?** В коммитах перебраны `10.0.0.1/8`, `172.31.254.1`, `172.20.0.2/16`. `10.0.0.1/8` конфликтует с типовыми LAN и гостевой сетью Keenetic — коммит `c885ecf` как раз про это. Нужно выбрать один и зафиксировать.
2. **NAT: `ndm` или `iptables`?** Журнал v1.0.6 говорит «отдать `ndm`», текущий код — обратное. Смешивать нельзя.
3. **Модель роутера и объём ОЗУ.** От этого зависит, критична ли C3 сама по себе (128 МБ — критична однозначно) и какие ключи оптимизации выбирать.
4. **Правки C1/C2 затрагивают общий код всех платформ** (`net_interface.h`, `websocket_client.cpp`), а не только сборку под Keenetic. Либо принимаем это как улучшение для всех платформ (обоснованно — spin-loop плох везде), либо прячем за `#ifdef`. Первое чище.
